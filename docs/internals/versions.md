# THPS3 recomp: ROM versions and code classes

One release of Tony Hawk's Pro Skater 3 (N64) is supported: **USA**. It is the only dump we have, so no other release (for example a
European one) is claimed or tested. THPS3 uses the same version scheme as THPS1 and THPS2: a **version** is a ROM we recognise (a row of
`decomp/common/games.toml`), a **code class** is a set of recompiled functions (one generated payload), and the host reads **names**
from a generated table (`thps::sym()`) and **facts** from `thps::version()`. A difference in behaviour becomes a named field in those
tables, never a version test in C++. Facts only here: hashes, addresses, names.

The app identifies a dump by hash (`.z64`, `.n64` and `.v64` are accepted). The row is `thps3` in `decomp/common/games.toml`
(`game_id` `thps3.n64.us`); the app keeps a copy of the dump in the config folder as `thps3.n64.us.z64`.

## The profile

Since ADR 0006 THPS3 has no host sources of its own: the host is `decomp/common/host`, and `decomp/thps3/recomp-host/` is a profile.
Its version tables are generated exactly as THPS2's are (`tools/gen_versions.py`, a wrapper of the shared tool; `check` validates them,
`header` writes `build/gen/thps_versions.h`).

<!-- table-ok: list of files of the version mechanism -->
| File | What | Edited when |
|---|---|---|
| `decomp/common/games.toml` | the row `thps3` | a version is added |
| `recomp-host/game/game.toml` | names, config folder, flags (`overlays = true`, `b_is_flip_in_game = true`) | rarely |
| `recomp-host/versions/classes.toml` | the one class, `us`: the `game` row and the `syms` file | a code class is added |
| `recomp-host/versions/host_syms.toml` | the names the host needs: 17 `funcs`, 1 `overlay_funcs`, 4 `addr`, 5 `field` | the host starts using a new address |
| `recomp-host/versions/us/host_force.toml` | `[force]` names by address, `splits`, `[overlay_force]` (`t2_intro+0x18C` is `Ovl_IntroUpdate`), `[cop2]` patch sites | a hook is added |
| `recomp-host/versions/us/data_syms.toml` | `[addr]` data addresses (`gSControl` `0x800EF794`, `gSkater` `0x800EF3AC`, the two Expansion Pak texts) and `[field]` struct offsets | a name is added |
| `recomp-host/versions/us/overlay_table.inc` | the class's overlay table (names, ROM offsets, sizes, blob offsets: numbers only) | regenerated by `tools/gen.py` |
| `recomp-host/config/thps3.hooks.toml` | the `[[patches.hook]]` blocks, by function name | a hook is added |
| `recomp-host/recipes/us/` | the first-run recipe, see below | the symbol file or the forced names change |

Generated into `recomp-host/build/gen/` (never committed; the C is ROM-derived): `thps_versions.h`, `us/thps3.host.{syms0,syms}.toml`,
`us/thps3.host.blob.bin`, `us/thps3.host.toml`, `us/RecompiledFuncs/`, `us/namespace.h`, `rsp/n_aspMain.cpp`.

The boot segment is THPS2's except three words, so the loader and libultra addresses in `[force]` are THPS2's. The front-end screens are
16 relocatable overlays, as in THPS2 ([overlays.md](overlays.md)); `Cop2_GteLoad` is the one function with coprocessor-2 leftovers.

## The first-run recipe

The downloaded app builds the game from your dump (the split build, ADR 0005). THPS3 needs one recipe, `recomp-host/recipes/us/`:

| File | What |
|---|---|
| `thps3.host.syms.toml` | function names, addresses and sizes (the symbol file with the host's forced names; the front-end screens are not in it) |
| `blob.txt` | XXH3-64 fingerprint of the code blob (a hash, not data) |
| `overlays.txt` | the 16 front-end screens: names, ROM offsets and sizes, relocation-stream offsets, the function map, and a fingerprint of the ROM range they cover |

The screens' bytes and relocation streams are read from the user's ROM at first run (`decomp/common/firstrun/overlay_rom.cpp`); the recipe holds
only the layout. A dump whose screens do not match the fingerprint is refused. The release zip carries this recipe;
`tools/package_split.py --refresh-recipes` rewrites it from the committed tables (needs the ROM, once per symbol change).

## Adding a release

Probe the hashes and the geometry; if the main image, its entry or its BSS end differ, it is a new code class. Add a `games.toml` row and a
`classes.toml` entry, seed the symbol file from `us` by signature matching (THPS2's `tools/seed_class.py` did this for its Europe class; see the THPS2 repository's
`docs/internals/versions.md`; THPS3 does not carry the script), fill in `versions/<class>/`, and run `tools/package_split.py --refresh-recipes --class <class>`. No host source
changes. We have no second dump, so none of this has been done for THPS3.

## Not covered

- Other releases: none known to us.
- Real PAL: not applicable, since only a USA release exists.
